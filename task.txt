# 1. CORE PRODUCT CONCEPT

LocalFix should work like a **Rapido/Uber-style service marketplace**, but instead of transporting passengers, customers request local home and maintenance services.

There must be **three completely separate roles and experiences**:

1. CUSTOMER
2. WORKER
3. ADMIN

Customer and Worker experiences must be treated as separate applications/interfaces even if they share the same backend.

Do NOT create one combined dashboard with conditional sections.

Use proper role-based authentication and backend authorization.

# 15. WORKER LOCATION SHARING

Worker location should NOT be tracked continuously without permission.

Location sharing begins only when:

- Worker accepts an active job
- Worker starts travelling / enables "On the way"

Location sharing ends when:

- Worker reaches customer
- Worker cancels
- Job is completed
- Tracking is manually stopped
- Booking expires

Ask for appropriate location permission.

Do NOT continuously track workers when they are off duty.

# 23. END-TO-END ENCRYPTION / SECURITY

Security is extremely important.

Implement the strongest practical security supported by the existing architecture.

Requirements:

- HTTPS/TLS in production
- Secure password hashing
- Secure authentication tokens/sessions
- HTTP-only secure cookies where applicable
- CSRF protection where applicable
- Role-based backend authorization
- Input validation
- Output sanitization
- Rate limiting
- Secure file uploads
- Access control
- Secure API endpoints
- Protection against IDOR
- Protection against unauthorized booking access
- Protection against privilege escalation
- Secure location access
- Minimal location data retention
- Audit/security logs

### IMPORTANT

Do not falsely claim that the application is "end-to-end encrypted" unless the actual architecture provides true end-to-end encryption.

If true E2EE is implemented for private chat:

The server must not possess the plaintext encryption keys necessary to decrypt message contents.

For normal HTTPS/API traffic, use TLS.

Clearly separate:

- Transport encryption
- Database encryption
- End-to-end encryption

Do not compromise security merely to make implementation easier.

# 33. API SECURITY

2. User identity
3. User role

# 34. ERROR HANDLING

The application must not break in the middle of an event or booking.

Every important operation should have:

- Loading state
- Success state
- Error state
- Retry mechanism where appropriate
- User-friendly error message

Examples:

If location fails:

"Unable to access your location. Please enable location permission or enter your address manually."

If worker location temporarily disconnects:

"Worker location temporarily unavailable. Last updated 20 seconds ago."

Do not crash the dashboard.

# 36. OFFLINE / FAILURE HANDLING

The application must fail gracefully.

If the worker loses internet:

- Preserve the active booking state.
- Show "Connection lost."
- Attempt reconnection.
- Do not duplicate booking requests.

If the customer loses internet:

- Preserve booking information.
- Reconnect automatically.
- Refresh booking state from the server.

Backend remains the source of truth.

# 44. MOST IMPORTANT PRODUCT PRINCIPLE

LocalFix should feel like:

**"Uber/Rapido for local home services."**

But the system must be designed specifically for service work.

The core experience is:

CUSTOMER
→ Requests a service
→ Nearby/suitable workers receive it
→ Worker accepts
→ Customer chooses worker
→ Customer sees worker profile
→ Worker travels toward customer
→ Customer sees live/near-real-time location
→ Worker arrives
→ Service is performed
→ Service completed
→ Payment
→ Customer reviews worker
→ Future customers benefit from trustworthy ratings

At the same time:

WORKER
→ Receives relevant jobs
→ Accepts jobs
→ Navigates to customers
→ Performs work
→ Gets paid
→ Builds reputation

And:

ADMIN
→ Protects the marketplace
→ Handles complaints
→ Verifies workers
→ Monitors bookings
→ Controls platform rules
→ Resolves disputes
→ Maintains trust and security

Build this as a **production-minded, secure, role-based marketplace**, not just a collection of UI screens.

After implementation, verify the entire customer → worker → admin lifecycle end-to-end and ensure existing LocalFix functionality remains intact.
